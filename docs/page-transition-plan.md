# 全应用页面过渡、占位与增量内容方案

状态：已迁移共享页壳、列表、详情和重内容渲染器。本次验收按要求使用代码检查。第七节保留真机和性能验证方法，供实测时使用。

## 迁移前的表现和定位

- [路由动画](../app/src/navigation/GithubAppNavigation.kt) 已经给出前进滑动结束事件。保留[前进期间不挂载重正文的决策](../.pensieve/short-term/decisions/2026-11-26-defer-cached-card-rendering-until-route-entry-finishes.md)：可以读数据，不在滑动中创建 WebView、排版长文档或构建 diff。比起把全部内容提前画在透明层后面，这才真正省掉入场成本。
- 原有 `GithubDetailPresentation` 按数据、布局、可见文档和进度揭开页面，分页又按路由和两个帧回调隐藏快照。迁移后，页壳直接绘制当前分区，卡片和文档各自在内容可画时交接。[页壳](../ui/src/navigation/GithubListPage.kt) · [分页](../ui/src/component/GithubPagingContent.kt)
- [GithubPageState](../ui/src/navigation/GithubPageState.kt) 在创建 presentation 时就登记 key，而 `detailPresented(key)` 查的是 key 是否存在。这不能区分「刚开始加载就离开」和「用户已看到内容」。
- [CommitDetailPage](../feature/commitdetail/src/CommitDetailPage.kt) 按 section 创建详情 presentation；Details 首次展示要求 Parents 和关联 PR 两路都就绪，页头的占位和正文各建一份分段控件。`select()` 只更新 section，不直接调用 `load()`；但 `revalidation(section)` 在组合中调用，非 Details 分支每次调用都新建 eager `stateIn(viewModelScope, …)`。这里既有可见交接问题，也有真实的重复订阅风险，不应笼统归因为“切换重新请求了一遍”。
- Issue 录屏第 78 帧已经显示作者和表情，第 92 帧卡片已撑高而正文还没显示，第 93 帧才有正文。[正文覆盖层](../ui/src/component/placeholders/LoadingTransitions.kt) 的槽高在 `loading` 结束时直接取 `body.height`，透明度另行推进。滑入时的重影则要对照设备原始录屏和 FrameTimeline，不能从转发视频反推是哪一层绘制出错。

## 1. 所有权和身份

| 所有者 | 身份与寿命 | 能改变什么 | 不能改变什么 |
|---|---|---|---|
| 路由栈 | 每次 push 的 route entry；出栈释放 | 两个页面的位置、裁剪、前后台输入权、首次重内容挂载许可 | 不改查询状态，不把已显示内容标为 loading |
| 页壳 | 同一路由内一份 | 顶栏、返回、标题槽、分段控件、工具栏；各自真实可用性 | 不因切 section、刷新或子文档失败替换整棵树 |
| 内容分区 | route entry 内的 section 或查询身份 | 自己的列表、空态、错误、滚动锚点和首次呈现记录 | 不控制兄弟分区和页壳；不拿另一查询的结果冒充当前结果 |
| 卡片与字段 | 同一数据源内的实体 ID；文档另加内容 revision 和布局环境 | 卡片骨架交给基本信息，晚到字段在自己的位置出现 | 不因补了摘要或附件而创建新卡、重播标题或改点击身份 |

路由负责滑入与恢复，分区保存首屏身份，卡片负责骨架交接。滑入期间占位保持静态。分区已呈现过时直接恢复缓存行。分页骨架交给实体时只播放卡片过渡，真正新增的实体使用列表插入动画。

**必须分开记录三件事：** 数据是否存在、当前渲染实例是否可画、这个身份的内容是否已经呈现。创建对象、数据非空和退出动画结束都不等于已呈现。仅在活动分区排版完并实际提交内容绘制后登记呈现；Compose 用该内容的首次绘制回执，WebView 还要校验文档 revision 对应的可绘制回执和非零测量。回执幂等，不在每帧写状态。取消或过期回调不得推进新身份。已呈现标记不能代替丢失的内容快照。

## 2. 每条用户路径应当看见什么

| 事件 | 画面 | 数据和交互 |
|---|---|---|
| 新页面前进 | 同一个轻量页壳随页面滑入；已知标题/导航控件用真控件，未知内容在原槽占位。整页不淡入或缩放 | 可以取数；滑动结束才挂载重内容。每个页面各自裁剪、使用不透明底和自身背景采样；系统栏保持原位 |
| 首次挂载或慢网 | 已缓存和刚加载的数据共用同一套静态骨架交接。各分区独立完成交接 | 缓存立即参与排版，首屏骨架至少保留 380 ms。空、失败也是终态 |
| 切同页分段/筛选 | 页壳和控件保留，分段指示器响应选择。首次呈现的列表使用首屏交接，已呈现的列表恢复原画面 | 快速 A→B→A 以最后选择为准，旧请求可回填旧 key |
| 返回、预测返回预览或取消 | 直接展示对应页面最后已呈现的分区和锚点，不走新页面骨架。取消后前台内容不重播 | 预览层不抢输入、焦点、无障碍焦点，也不因预览触发业务刷新；真正激活后按现有刷新策略静默更新 |
| 刷新、追加、失败、重试 | 有内容就保留。追加只用尾槽；失败只在失败区域给可操作状态。首次成功且零条才显示业务空态；业务明确约定的降级文案单独保留 | 区分首次请求、后台校验和追加；只重试失败的数据源。权限撤销、删除、注销不保留旧私有数据 |

若设备原片仍有非预期重影，分别检查路由裁剪、两个页面的背景采样和顶栏、底栏图层，不叠加额外遮罩。

路由动画与 [YumeBox `AppNavContainer.kt`](https://github.com/YumeYucca/YumeBox/blob/4a6bb76e9f6956cd56e692e0f381652db608fad9/app/src/presentation/navigation/AppNavContainer.kt) 使用相同的 Decompose 实现：普通进退栈组合淡变、滑动和缩放；预测返回交给 `androidPredictiveBackAnimatableV1`，顶栏跟随同一份手势进度。
普通转场沿用 Decompose 的输入策略。出栈时停止页面交互，等退场页离开组合再清理其 ViewModelStore。当前窗口和账号最多暂存两个已绘制的内嵌 Markdown WebView；仅同一路由、文档、配置和测量尺寸匹配时复用。只命中高度不表示正文已可画，新 WebView 仍需等待自己的首帧。

## 3. 占位的形状和边界

- 占位不再仿造 Card 的圆角、边距、字段槽或实体布局；用页面级通用骨架表达“正在加载”，不承载业务内容，也不与卡片身份或尺寸动画绑定。
- 骨架使用静态低对比色块。列表按需用圆形和短线，文档按需加大块占位。
- 占位不接受点击、无障碍焦点或文本选择。首屏立即显示骨架，再次等待超过 120 ms 才显示。骨架退场和正文出现共用一条弹簧曲线，较小的槽高差同步缓动。
- 代码文件、代码搜索和详情区块在固定槽里交接。搜索选择面板的等待与结果列表共用一个槽，已有重试入口的面板在原槽显示重试。Markdown 在页面滑动期间保留同一个渲染占位，滑动结束后再挂载正文。

## 4. 增量 Card：按“能不能独立阅读”分两类

**列表摘要卡**（Issue/PR、通知、动态、提交摘要、仓库）：标题和基本元数据独立于摘要、参与者和统计。首屏字段作为同一个内容层出现。晚到的字段从原位置淡入并展开，已出现的字段保留位置和点击身份。同一批字段只驱动一次高度变化，数值更新就地替换。已呈现的列表滚出再回来直接绘制快照。

封面间距随图片或对应占位一起参与布局。缺少可用封面时，标题行紧贴卡片原有顶部内边距。

**阅读卡**（Issue/PR 描述、评论、Discussion 正文、README、Release 说明）：主要阅读单元是文档，不是反应按钮。卡框保留；如果作者已知，可先显示并固定在顶部。卡内只留一次正文占位；正文尚不可画时不先显示文章末尾的表情、操作区。渲染器只挂载一个实例，独立测量。高度差较小时，正文淡入与槽高缓动共用一个进度；高度差较大时，直接提交可读正文与最终高度。文档失败用局部错误和重试结束等待，不能封锁标题或整页操作。

**恢复不是入场。** 已绘制过的文档重新挂载时，复用同 revision、宽度、字体缩放及布局配置的测量结果稳住槽位；可见文档按现有保留策略复用，有效画面没有准备好时只能展示真实的待恢复状态，不把过期像素伪装为新内容。不缓存整个页面位图或全栈 WebView。关闭动效时用完全相同的状态转移，直接提交最终布局。

骨架和正文共用一个布局槽。骨架淡出并轻微虚化，正文同拍淡入，从 99% 回到原尺寸，同时从 4 dp 模糊变清晰。槽高相差超过 320 dp 时使用最终高度。参考 [Screenrove Skeleton swap](https://screenrove.com/motion/interior-skeleton-swap) 和 [interior.dev 原组件](https://www.interior.dev/docs/skeleton-swap)。

## 5. Commit 作为第一条端到端路径

1. `CommitDetailPage` 只建立一个页壳和一个真实的 Files / Details 控件；没有选择回调为空的占位副本。标题读取 commit；作者卡属于 Files 正文，不再作为两种分区都要重新测量的页头。切换后允许内容和选中状态重组，不允许页壳销毁或重播入场。
2. Files 独占文件分页；Details 不再包装一个空的 `PagingData`。Details 的作者和 hash 随 `detail` 展示；Parents 和关联 PR 是两个独立分组，各自提交加载、内容、空、失败。点其中一个重试不重载 commit、文件和另一个分组。
3. 在 ViewModel 按数据源持有稳定的 flow；按需开始订阅，同一个 key 至多一个上游。移除 `revalidation(section)` 调用即创建 eager 流的路径。区分 UI 分段 `Files / Details` 和实际数据源 `Files / Parents / PullRequests`；切换只更新所选分段，重新收集不等于重新拉网。
4. 用现有 route entry 保存两个分区的快照、各自的首个可见实体加 offset、顶栏折叠位置和文件展开状态。展开键含文件身份和 diff 版本，不含列表索引、loading 或页签。未变版本返回时保持展开；新版本不得拿旧 patch 冒充。后台列表可释放组合，不靠永久挂载两个列表保状态。
5. 验收手势：展开文件并滚入 diff 中段 → 切 Details → 让 Parents 迟到或失败 → 切回 Files。标题和控件从头到尾只有一份；hash 不等 Parents；回到同一文件、同一展开状态、同一锚点，零帧骨架、无新增同键上游、无切换引起的网络刷新。连续快切和加载未完即返回单独测。

## 6. 落地顺序和覆盖边界

| 交付 | 修改边界 | 退出条件 |
|---|---|---|
| 1. 基线与共享规则 | 登记所有路由、页内切换、加载卡/增量字段和重渲染器，按本表指定所有者；记录 Issue 原片和 Commit 原始真机路径。拆开 `GithubPageState` 的已创建/已呈现；把入场许可集中到导航宿主及重内容挂载边界 | 事件可区分 push、切分区、恢复、刷新、字段补齐；单独哪个业务页都不能再发起第二次整页揭开 |
| 2. 两条参考实现 | Commit Files/Details；Issue 列表→详情→返回。贯通 `GithubPage`、`GithubListPage`、分页快照/槽键、阅读卡与 Markdown 回执 | 下列帧级断言和状态恢复断言同时通过，才批量迁移 |
| 3. 搜索与列表族 | Home、Explore、Discovery、通知、搜索/Issue 搜索、Issue/PR 列表、仓库/收藏/集合、工作区、提交历史、仓库动态等 | 每个筛选/查询身份单独恢复；首批、追加、空、失败和已显示后刷新符合相同规则；列表调用点与卡片不重复包装同一交接 |
| 4. 详情与专用面板 | PR 分区、Discussion、Release、仓库/个人资料和 README、PR commits/diff、Actions、文件/编辑器预览等；静态设置、认证、弹层只采用适用的页壳/输入规则，不增设骨架 | 每个路由登记为已验证或有理由不适用；重型内容都有独立首帧、失败、恢复路径，非活动页不触发请求或抢焦点 |
| 5. 删除旧路径 | 按所有者替换 `GithubDetailPresentation` 的全页进度、`independentBody` 分叉、调用点到处读取导航就绪、分页固定帧等待、重复 loading 容器与骨架树。复用现有稳定槽键、快照和缓存失效逻辑 | 调用点清单归零或有明确保留理由；不是新旧两套策略长期并行。按模块替换，与已有卡片变更合并，不重复实现 |

保留状态按账号、资源、查询/section、版本隔离；复用现有有界路由缓存。路由出栈释放该 entry 的 UI 状态；账号变化清空相关快照。配置变化恢复身份和锚点，重算失效尺寸；进程死亡只恢复可保存的导航与轻量交互状态，有持久数据才恢复正文，否则按真正冷启动处理。

## 7. 验收：帧证据优先于编译结果

- **可控 UI 测试**：分别延迟基本数据、增量字段、分页和文档首帧；使用 Compose 测试时钟在切换前、中、后采样真实槽边界、正文可见区、交互和语义。断言同一页壳不 dispose/recreate、同一控件不出现两份、已呈现内容不回到骨架、晚到字段不改变标题位置、长文不产生先扩高却没有内容的帧。不要断言整页重组次数为零。
- **状态与请求测试**：依次覆盖冷进、暖进、普通返回、预测返回完成/取消、重复快切、滚出滚回、后台刷新/失败重试、分页追加、切账号、旋转/大字体、关闭动画。分别统计订阅创建、上游启动和实际请求；缓存未过期且无显式刷新时，重复切换不得增加网络请求数；合法的后台校验单列。
- **真机视觉门槛**：同账号/相同数据、同构建类型、相同刷新率和录制条件下，对照保存原始录屏，不拿社交软件二次编码当绘制证据。逐帧标出滑入、交接、恢复；不得看到旧页像素越过页面边界、标题/分段双影、已呈现分区闪骨架、先空白再出文、返回锚点先归零再纠正。分别覆盖长文、短文、无正文和慢加载。视觉证据不能由编译通过替代。
- **性能门槛**：用同条件 FrameTimeline/Perfetto 对照冷、暖路径的超预算帧、p95/p99 和最慢帧；按设备实际帧期限判断，不拿平均 FPS 当结果。滑入期间不得出现新页面重文档挂载；缓存切分段不得重建页壳、重复订阅或全页重排。若有回退，定位是组合、测量、WebView 还是合成，再放行该页面族，不靠加长动画掩盖。
